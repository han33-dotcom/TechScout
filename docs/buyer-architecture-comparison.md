# Choosing TechScout’s buyer architecture

**Decision as of 26 November 2026:** Keep the current buyer pipeline as the comparison baseline. The next experiment gives one shopping agent responsibility for the buyer’s request from interpretation through recommendation. Adoption depends on a paired comparison. Multi-agent coordination, model choice, and reasoning effort are later experiments.

The goal is a buyer who can find the right item, understand the tradeoffs, and see what they would pay. Choose an implementation on the accuracy of those answers, coverage across requests and sellers, cost per useful answer, and time to first useful result. This record connects each design choice to the evidence available when it was made. [Buyer contract](buyer-product-contract.md) · [Acceptance criteria](buyer-correctness-acceptance.md)

## Who makes each decision?

| Pipeline stage | Rule-based pipeline with LLM calls · implemented | One end-to-end shopping agent · proposed | Coordinating agent and seller workers · possible later experiment |
| --- | --- | --- | --- |
| Understand the request | The API applies patterns to the buyer’s wording and stores the model, hard constraints, preferences, destination, and unresolved clauses. | The agent interprets the original wording, retains constraints across turns, and asks a question when the answer could change the recommendation. | The coordinator interprets the request once and gives workers the same constraints. |
| Find listings | Code searches the catalog and supported retailer routes. For broader discovery, an LLM selects a query and channel from options prepared by code. | The agent chooses the next supported tool, sees the result, and can revise the query or try another merchant. | Workers investigate different sellers in parallel. The coordinator decides where another search could change the result. |
| Match and verify | Retailer readers extract the selected SKU, terms, and specs. Rules check the variant and eligibility. An LLM can select an evidence gap for another read. | The agent sees the buyer’s wording alongside selected-item evidence, proposes a match, and requests missing facts. Tools verify the supporting fields and calculate the total. | Each worker returns a proposed match with its retailer evidence. The coordinator checks comparability and resolves conflicting findings through the same tools. |
| Advise the buyer | Verified candidates can reach an LLM suitability selector and writer. Incomplete offers can appear as priced leads. The UI can render a deterministic summary. | The same agent explains the recommendation, presents a useful partial, or asks the buyer for a detail and resumes the search. | The coordinator synthesizes the verified results and owns the conversation. |

All three designs use the same buyer contract. Current price and stock belong to a specific variant. The retailer supplies delivery terms. The cost engine uses decimal arithmetic and preserves unknown charges. For a fair architecture comparison, share the evidence tools, retailer access, and workload and spending limits. ## What we have measured

**Earlier architecture comparison.** A 23-request study ran four configurations through shared retailer adapters and verification. The full system used a deterministic controller with scoped model roles and bounded research workers. Its warm and cold runs produced 69/69 and 23/23 abstentions. The historical single-agent runner made sequential reads within the existing evaluation flow and abstained in 69/69 trials. The fixed search/filter/recheck runner abstained in 68/69 and timed out once. Across 230 trials, buyers received zero priced matches. That study documents an actual design comparison. The proposed single-agent experiment changes who interprets the raw request and who can recover after a failed match. **Why test a different architecture?** On the H110 request the worker reached the correct $9 headset. The parser retained “stereo” in the model name, and matching discarded the retailer’s descriptive title. A shopping agent with access to both the original wording and the selected product could recover this match. It must also reject the JBL listing whose purchase form selected white when the buyer requested black. A separate monitor case had a $397.94 delivered quote outside the supported ITWorks monitor route. Expanding that route would be a tool-coverage change; record and test it for both implementations. ## How we will choose

1. **Isolate agent ownership first.** Run the current pipeline and the end-to-end agent on paired, freshly reserved requests with the same model, low effort, tool interfaces, source scope, budgets, and catalog starting state. First replay the same captured retailer evidence to isolate interpretation and matching. Then test through the ordinary buyer UI with live retailers. Recheck changed prices or stock and keep each original outcome.
2. **Score what reached the buyer.** Report correct page found, working priced listing shown, confirmed hard requirements, verified payable total, and correct seller comparison as separate counts. Include exact-model and needs-based requests, wrong-variant controls, useful partials, and explained blockers. Report delivered totals over all requests and over independently quotable requests. A misleading verified claim fails the existing acceptance gate. Its thresholds are 8/10 full, 4/5 partial, 5/5 blocked, and 4/5 seller pairs within the full group. [Scoring protocol](buyer-correctness-acceptance.md)
3. **Measure the tradeoffs.** For each arm record settled and uncertain spend, calls, cost per request and per useful answer, time to first useful display, final latency (median and p95), timeouts, and attainment of the 120-second target. Record “unreached” when no useful answer appeared. Inspect paired wins and losses and report sample size. Prefer lower cost and latency among designs with comparable correctness and coverage.
4. **Change one factor at a time.** If the single agent improves buyer outcomes, test whether parallel seller workers add coverage or reduce latency enough to justify coordination cost. Separately, hold architecture fixed while varying model at the same supported effort, or varying effort with the same model. Predeclare the candidate, the tradeoff it should improve, and fresh confirmation cases before tuning.
