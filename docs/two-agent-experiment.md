# Two-agent shopping experiment

The buyer agent owns the conversation and shopping decisions. A second agent builds the catalog once a day. Both inspect public retailer pages directly through Firecrawl, including pages on a shop's first appearance. The [buyer contract](buyer-product-contract.md), [18 acceptance scenarios](buyer-acceptance-matrix.md) and [frozen scoring protocol](buyer-correctness-acceptance.md) define success.

## Delivery

## Responsibilities

| Component | Decisions and outputs |
| --- | --- |
| Buyer agent | Start from the buyer's own wording, selected controls, destination and chat history. Interpret constraints and preferences, ask material questions, choose catalog and web searches, inspect competing listings, match the selected variant, assess tradeoffs and explain the answer. For a pasted deal, start with the exact URL. Preserve established constraints across revisions. |
| Catalog agent | On a daily trigger at a configurable local time in Asia/Beirut, find sellers and products and refresh due observations. Prioritize stale listings, gaps in category coverage and configurations with only one known seller. Reuse existing storage, checkpoints and leases for retries. First exercise the daily job on demand. Choose the operating hour when scheduling it. |
| Shared page inspection | Both agents start a new public listing with Firecrawl, including at first-seen shops. The agent assesses the capture against its objective. It can finish, read a retailer-published link with Firecrawl, or use Playwright to render the page or select an observed product option when further Firecrawl reads seem unlikely to help. The resulting capture must support the reported seller, configuration, price and stock. Shop stops, workload limits and shared accounting apply to both jobs. |
| Application and storage | Keep the original request, agent decisions and page evidence. Calculate comparable amounts with Decimal. Enforce evidence provenance, privacy and the existing time and spend budgets. Render and save useful partials while research continues. Preserve authoritative identifiers when supplied; a product family plus requested attributes can match a more detailed retailer title. |

A page read produces an observation with URL, UTC time, source response hash and the selected item or option evidence available on that page. A priced buyer claim points back to the evidence for that item. Public observations may enrich the shared catalog. Private addresses, chat content and buyer-specific quotes stay in the buyer's scoped records. Establish that the actual merchant is based in Lebanon and serves the requested destination. Recheck finalist price and stock during the buyer run. A delivery total also needs evidence for applicable mandatory charges. Integrate pending seller quotes through [#186](https://github.com/han33-dotcom/TechScout/issues/186) and the same-chat account flow through [#187](https://github.com/han33-dotcom/TechScout/issues/187).

If one inspection fails, keep previously supported same-run facts visible with their timestamps and explain the outstanding question. A contradictory observation, changed selection or changed price triggers reassessment. Online stock can support an explicitly labeled partial for pickup; branch stock needs branch evidence. Label incomplete totals and present evidenced alternatives when they help the buyer.

## First development journey

> I'm looking for new black Soundcore Q20i headphones. Which Lebanese shop has the lower total for one pair delivered to Batroun?

Use this fresh request for development. For the controlled rehearsal, give the catalog agent public sample evidence from synthetic shop A. Start a fresh buyer session after catalog ingestion. Its web search can discover synthetic shop B for the first time. Shop B is absent from the catalog and retailer registry. Only the independent evaluator knows the expected URLs, selected variant, prices and totals. Supply the buyer with the request and destination only.

Use a cheaper sibling color or nearby model on one storefront. Give one seller the lower listed price and the other the lower delivered total. The buyer must see the black Q20i at both sellers, the two exact links, selected-variant price and stock, applicable charges, comparable totals and the correct cheaper seller. Then withhold a mandatory fee and check that the priced offer survives with the fee labeled unknown. Include a later failed re-read and a separate contradictory successful read. The fixture is a controlled exercise; current commercial availability and a real seller pair remain to be established independently. Keep an unsuccessful live attempt in the results.

## Agent-directed inspection checkpoint

The buyer and catalog agents each choose the next read using the current evidence and their own objective. Both can finish after the first Firecrawl capture, follow a public same-shop link, or open Playwright. Playwright can render a page without clicking, select named product options using radio controls and dropdowns, and operate variant buttons that expose a name, value and pressed state. The agent receives the observed choices. A reported configuration must agree with the priced item in the captured page. The buyer can recheck the same configuration. The catalog records the reader, decision and receipt, including a failed follow-up or unavailable model decision.

The experimental offer refresh allows USD 1 per batch and USD 1 per job. Its configured model reserves about USD 0.0615 before dispatch for each decision. The ledger records actual spend after the call. The shared maintenance ceiling is USD 3 per UTC day. These figures apply to the development branch. ### Listed-price development experiment

Before making a permanent scope decision, test whether the buyer can find one qualifying listing, then compare two shops on the advertised item price. Give each fresh experimental buyer up to 300 active seconds. Keep the existing dollar and call allowances. Record elapsed time, early stops, and what the buyer actually sees. The original 20 delivered-total requests retain their own scorecard.

For one shop, require a matching exact item at a Lebanese merchant, a working product link, the current listed price and currency, online stock and evidence of the requested condition. For two shops, require the same requested configuration, independently owned sellers, both qualifying listings in the answer, and the correct lower listed price or tie. Retain a priced partial when condition or stock is unknown. Delivery fees are outside these two requests. A seller's listed price cannot stand in for an amount payable at checkout.

Use the normal buyer form wording and API/worker path. The evaluator checks the retailer references independently and keeps seller links and reference prices out of the buyer's inputs. Record any repeat with an explicitly populated model field as a diagnostic, separately from the scored natural-language submission. The existing full-product UI still labels incomplete payable totals as partial. Score the visible item evidence against the listed-price request and record the UI's actual disposition as well.

In the first scored request the buyer asked for one shop with new black Soundcore Q20i headphones in stock. The intake code took “one Lebanese shop” as the model. The catalog lookup missed its existing Q20i entry. The run returned zero offers after 123.1 seconds. With the same wording and an explicitly populated Soundcore Q20i model field, a fresh run returned IT Promax at USD 48 in online stock in 86.5 seconds. New condition was unverified.

The second scored request asked for two shops selling a new Logitech H111 wired 3.5 mm headset. The intake code kept the shopping instructions inside the model field. It exceeded the 64-character product-query limit, so the buyer's offered searches used general audio terms. It inspected category pages, exhausted its 16 shopping actions, and returned zero offers in 246.7 seconds. The independently inspected listings showed MobileLeb at USD 13 and JAK Computer at USD 25, both new and in stock. Logitech identifies both retailer part numbers as the requested single-jack H111. The original two development submissions therefore scored 0/1 on the single-shop request and 0/1 on the comparison.
