# TechScout buyer acceptance matrix

TechScout helps a buyer choose electronics from sellers based in Lebanon. A buyer can bring a model name, a retailer link, or a description of their needs. The agent should advise them the way a knowledgeable showroom salesperson would. It should use what it knows, ask when an answer would change the advice, explain tradeoffs, and revise its recommendation as the buyer responds. The buyer makes the purchase on the retailer’s site.

The [buyer product contract v1](buyer-product-contract.md) governs these pass conditions. The examples are development scenarios with illustrative prices. Each row still needs evidence. The [buyer rules audit](buyer-product-rules-audit.md) describes the earlier implementation and policy gaps.

## Buyer scenarios

| ID | Buyer situation | Observable pass condition |
| --- | --- | --- |
| 01 | “I want a big, powerful laptop.” | Ask about budget, intended work, and any specifications the buyer already has in mind. Accept ordinary language. Ask a further question if plausible meanings would lead to different advice. |
| 02 | “I edit 4K video, want a large screen, and can spend up to $1,200.” | Start showing suitable options and explain the specifications that matter for editing. The buyer can get advice without choosing a processor first. |
| 03 | After seeing two options the buyer says, “I carry it to university every day.” | Reassess weight, explain the tradeoff, and retain budget, workload, and destination. The conversation can continue through another refinement. |
| 04 | The buyer names an exact configuration. | Show the matching variant, price, availability, and a working link to that offer. A different memory, storage, or model suffix cannot silently satisfy the request. |
| 05 | The requested variant is unavailable among the sellers checked. | Show a near match when available, explain what differs and why it is being shown, and offer to search other models preserving the buyer’s priorities, such as 16 GB RAM and 512 GB storage. |
| 06 | “Is this laptop a good deal?” with a retailer link. | Identify the linked configuration and compare it with the same configuration at other Lebanese sellers. If none can be verified, explain the comparison’s limits. |
| 07 | Two otherwise comparable offers differ in delivered price and documented warranty. | Identify the cheapest, explain the premium and what the buyer gets for it, and ask whether warranty matters when it could change the pick. Revise the recommendation after feedback. |
| 08 | The buyer says “up to $750.” One shop quotes $745 delivered and another lists $730 before an unknown fee. | Show the complete and promising incomplete offers with their status, links, and missing fact. Flag that the second could exceed budget. A known $755 total cannot qualify. Repeat with “around $750” and verify that a small overage can be explained as a tradeoff. |
| 09 | New condition is requested or the buyer leaves condition unspecified. | Treat new as the default. Unknown condition can appear as a labeled lead. Recommend a refurbished item as eligible only after the buyer opts in. |
| 10 | A Lebanese seller serves Tripoli and publishes an applicable fee. The warehouse is unspecified. | Use the actual seller’s identity and service area. Use the seller’s fee once, regardless of warehouse location. On a marketplace, verify the actual merchant before including it as domestic. |
| 11 | City selection gives one seller’s quote. Two other sellers need a street address. | Show the first quote promptly. Name both remaining sellers and explain once why a more precise address could change the comparison. |
| 12 | A signed-in buyer has multiple saved locations. | Let the buyer select the address for the named sellers and current search. Recompute the comparison for that destination using the sellers’ responses. |
| 13 | A buyer has a TechScout account and no saved address. | After login, follow the chat’s address prompt to the locations page, add one or more addresses, select one, and return to the same chat. Resume the pending quotes and recommendation automatically. A later signed-in search can reuse a saved address. Exercise account creation separately with a new buyer. |
| 14 | The buyer declines to provide a precise address. | Continue with the best available offers and explain which delivery totals remain uncertain. The buyer can still open the product links. |
| 15 | The fee appears only in pre-order checkout, or the retailer never provides a usable quote. | In the first case, obtain the item-, quantity-, and destination-specific quote before payment or order and update the totals. In the second, preserve the unknown. TechScout does not place orders, pay, reserve, create retailer accounts, or message sellers. |
| 16 | The buyer requests pickup at a named branch or switches branches. | Bind availability to the requested variant and branch. If only online stock is known, say so and provide the branch’s published number when available. Recheck after a branch change. |
| 17 | A finalist’s price changes or its stock cannot be confirmed during the search. | Use current-run price and stock evidence for a verified recommendation. Update the result or label the missing or conflicting fact. An arrival estimate cannot satisfy a guaranteed deadline. |
| 18 | Two sellers carry the same variant, or the search finds no qualifying offer. | With comparable delivered totals, identify the cheaper seller or a tie and link both exact offers. When none qualifies, explain what was checked and why. Do not claim market-wide unavailability. |

## How a task earns acceptance

- **Repeatable scenarios.** Use offline retailer fixtures for each branch in the relevant rows. Judge what the agent asked, retained, showed, and supported with evidence. Allow different sensible wording. Assert both the resulting recommendation and any claims that would mislead the buyer.
- **Browser walkthroughs.** Exercise the ordinary buyer interface across turns. For the address round trip, capture the visible comparison before and after, verify the selected destination and retained constraints, and use a test address in the evidence. Include the saved-address and decline paths. Record the product revision and whether seller responses were fixtures or live.
- **Live shopping evidence.** The first useful exact-model result belongs to [#176](https://github.com/han33-dotcom/TechScout/issues/176), one fully verified offer to [#75](https://github.com/han33-dotcom/TechScout/issues/75), and a comparable two-seller result to [#177](https://github.com/han33-dotcom/TechScout/issues/177). Link the applicable rows, dated retailer evidence, and buyer-visible run to each task. A complete address walkthrough is a distinct product task.
- **Held-out evaluation.** [#178](https://github.com/han33-dotcom/TechScout/issues/178) requires a frozen 20-case set before debugging and scoring after the live checkpoints. Pass at least 8/10 fully verifiable cases, 4/5 useful partials, 5/5 correctly explained blocked cases, and 4/5 two-seller comparisons within the verifiable group. Any misleading verified claim blocks acceptance. Record timing separately from correctness.
